What the orchestrator sends each processor

PAYMT-520 · 11 situations captured from github.com/Unicity/frontier's own charge code on 9 Nov 2026 · highlighted fields change with the situation

These are the exact requests the in-house orchestrator's own charge code builds for each processor, captured by running the real adapters (packages/payments-service-domain/src/processors, github.com/Unicity/frontier main, 9 Nov 2026) with a recording stand-in for the network. Nothing was sent to any processor. Card numbers are the published test card, shown masked; the CVV is masked; credentials are placeholders and never appear.

Why not real QA transactions?

  • No log keeps them. The service's own rule: "No adapter logs a body". The processor log line names only the operation, the order code and the answer's kind (apps/payments-service/docs/processor-requests.md).
  • The service's logs are not in our Datadog. 0 lines for payments-service, payments-portal-service, payments-merchant-demo-service and cart-service over 14 days (us5, read 9 Nov 2026).
  • The database keeps only the outcome. Each attempt stores brand, expiry, fingerprint, decline code, processor transaction id, response code and message, scheme transaction id and the 3-D Secure result; never the request.
  • So the only place a real QA payload can be seen is at the processor: the NMI merchant portal (test transactions under the QA user on the same gateway host), the Worldpay test Merchant Interface, and the Nuvei sandbox control panel. Each needs your sign-in.

What the payloads show

  1. Nobody keeps the payload. Teller's full wire bodies are in Datadog today; this service keeps none, in logs or in the database. A disputed or failed charge cannot be checked field by field after the fact. Proposed owner: Matthew Winn, to accept or reassign.
  2. Worldpay rebills still send the shopper session. WP-4 carries <session id shopperIPAddress> on a merchant-initiated rebill; the team's own processor-requests.md says a rebill sends "no CVV, session or browser". The element is unconditional in worldpay/build.ts (line 212). The same defect was fixed on teller under TKT-7341. Proposed owner: Matthew Winn.
  3. NMI test and live share one host. Only test_mode=enabled, added when the account is in Test mode (nmi/index.ts line 26), keeps a test charge from being real; the credentials decide the rest.
  4. Done right: card data only in the body, never the URL (the teller NMI defect TKT-7331 does not exist here); no CVV on rebills; stored-credential flags follow who started the charge; the NMI order description is the merchant reference, not the full stop teller sends (TKT-7586).
  5. Questions, not findings: the Worldpay phone-order body has no phone-order marker and relies on the MOTO merchant code (inference: confirm with Worldpay); the test seed sends US phone orders to NMI unicityecom; production's phone account is set in the portal and NOT ESTABLISHED.

Not captured: Braintree and PayPal (GraphQL and REST calls that need live tokens from the browser), Apple Pay and Google Pay (need wallet tokens), and the Worldpay 3-D Secure completion call. The builder of this page: build\payloads\capture_payloads.ts (run with Bun in the read-only clone) and render_payloads.py.
